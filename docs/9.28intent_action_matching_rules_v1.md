# Intent–Action 批量匹配规则 v1

## 目标

对同一 Thought step 中的原始 Action 和当前应执行的 Intent（`match_eligibility=due_now`）建立多对多覆盖关系。一个 step 可以有多个 Intent，一个 Action 可以对应一个或多个 Intent；只要所有 `due_now` Intent 都被至少一个 Action 覆盖即可。没有合理 Intent 时标记为 `no_intent_match`。模型输出是初步标签，不能直接视为人工 Gold。

## 输入与候选范围

1. Action 必须使用完整 raw Action，包括完整 `function` 和 `args`。
2. 候选 Intent 只能来自相同 `trajectory_id` 和 `thought_step`。
3. 只允许选择 `due_now` Intent；`future`、`conditional_unresolved`、`uncertain` 不得作为匹配结果。
4. Action 结构审计字段（`atomicity`、`action_has_extras`、`requires_manual_semantic_review`）必须保留。
5. `split_safe` fragment 只能用于辅助理解，不能替代 raw Action，也不能单独生成匹配样本。

## 判定顺序

模型按以下顺序判断：

1. Action 是否完成了 Intent 的核心操作。
2. Action 的目标对象、路径、URL、文件名或实体是否与 Intent 一致。
3. Action 的关键约束是否满足，例如来源、目的地、范围、格式和参数。
4. Action 是否包含 Intent 未要求的额外操作。
5. 如果 Action 只完成 Intent 的一部分，标记 `partial_match`。
6. 如果操作类型相同但目标对象不同，标记 `object_mismatch`。
7. 如果目标对象相同但操作类型不同，标记 `type_mismatch`。
8. 如果没有任何当前 Intent 合理支持该 Action，标记 `no_intent_match`。

## 多 Intent 与多 Action

- 每个 Action 可以选择一个或多个 `selected_intent_ids`。
- 一个 Intent 可以被多个 Action 覆盖；这表示该 Intent 可能需要多个动作完成。
- 一个 step 有多个 Intent 和多个 Action 时，建立稀疏覆盖关系，不把所有 Intent×Action 组合都当作匹配。
- 一个 Action 可以同时覆盖多个 Intent，但必须在 `reason` 中说明每个 Intent 的可见证据。
- 同一步的所有 `due_now` Intent 最终都必须有至少一个覆盖 Action；没有覆盖的 Intent 生成 `uncovered_intent` 记录。
- 两个 Intent 都合理但证据不足时标记 `ambiguous`，并列出 `alternative_intent_ids`。
- `composite_unsafe`、多个候选接近、关键目标无法确认时必须 `review_required=true`。
- 没有 Action 的 Intent 另行生成一个 `no_action` 记录，不伪造 Action。

## 标签

允许的 `label`：

- `exact_match`：Action 完整实现 Intent 的核心操作和目标。
- `partial_match`：Action 只实现 Intent 的一部分，或缺少关键约束。
- `object_mismatch`：操作类型基本一致，但目标对象不一致。
- `type_mismatch`：目标可能相关，但操作类型不一致。
- `no_intent_match`：没有当前 Intent 支持该 Action。
- `ambiguous`：多个 Intent 同样合理，无法可靠区分。

## 置信度与人工审核

- `confidence` 为 0 到 1 的数值。
- `confidence < 0.80` 必须人工审核。
- `ambiguous`、`partial_match`、`no_intent_match`、`composite_unsafe` 和多候选 Action 必须人工审核。
- 模型必须给出简短 `reason`，引用 Action 和 Intent 的可见证据，不得使用隐藏环境信息。

## 输出格式

每个 Action 输出一条 JSON：

```json
{
  "trajectory_id": "...",
  "thought_step": 1,
  "action_id": "call-001",
  "selected_intent_ids": ["T1-I2"],
  "covered_intent_ids": ["T1-I2"],
  "label": "exact_match",
  "confidence": 0.93,
  "reason": "The action reads the requested input directory.",
  "alternative_intent_ids": [],
  "review_required": false
}
```

无匹配时 `selected_intent_ids` 为空数组；不确定时使用 `ambiguous`，并列出 `alternative_intent_ids`。每个 step 还必须输出覆盖审计：`due_now_intent_ids`、`covered_intent_ids`、`uncovered_intent_ids` 和 `coverage_complete`。`coverage_complete=true` 仅表示所有当前 Intent 都至少被一个 Action 覆盖，不表示每个 Action 都是精确匹配。

## 禁止事项

- 不根据后续 Thought 或后续 Action 反推当前 Intent。
- 不把未来计划当作当前匹配。
- 不修改、截断或标准化替换 raw Action。
- 不把模型初步标签直接称为 Gold。
- 不用模型生成 Action 中不存在的目标、参数或执行结果。

## Intent 去重与多目标规范

1. 同一 Thought step 内，只有在以下字段都相同或等价时才合并 Intent：操作类型、目标对象、关键约束、时间范围和预期结果。
2. 仅措辞不同不构成不同 Intent。例如 `Read input/config.json` 与 `Inspect input/config.json` 可以合并。
3. 目标不同的 Intent 不得合并，即使它们共享同一个 `source_quote`。例如 Kenya、India、Germany 三个目标必须保留为三个 Intent。
4. 如果一个 Intent 文本包含多个可以独立执行的目标，应拆成多个 Intent，并保留同一个 `parent_intent_group_id` 和不同的 `target_key`。
5. 去重不得只根据文本相似度、source quote 或操作动词判断；必须比较操作、目标、约束和 temporal scope。
6. 合并或拆分后必须重新生成 Intent ID 和 `validated_intent_sha256`，并保留 `revision_type`、`parent_intent_id` 或 `parent_intent_group_id`。

## 覆盖完整性与问题标签

1. 每个 Thought step 必须计算 `due_now_intent_ids`、`covered_intent_ids`、`uncovered_intent_ids` 和 `coverage_complete`。
2. `coverage_complete=true` 仅表示每个当前 Intent 至少被一个 Action 覆盖，不表示所有覆盖都是 exact match。
3. 当前 Intent 没有任何 Action 覆盖时标记为 `uncovered_intent`；不要把它和 Action 没有对应 Intent 的 `no_intent_match` 混淆。
4. 一个 Action 覆盖多个 Intent 时，必须为每个 Intent 提供可见证据；顺带相关不能直接标为 exact match。
5. 一个 Intent 被多个 Action 覆盖时，必须区分必要的多步执行和重复执行；重复执行应标记 `duplicate_action_coverage`。
6. 复合 Action 可以覆盖多个 Intent，但 `composite_unsafe`、目标无法拆解或包含额外操作时必须 `review_required=true`。
