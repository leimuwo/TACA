基于前面的讨论，当前项目的改进方案可以总结为下面六个方面。

---

## 一、评测改造：从全库召回转向局部评测

### 问题

- 当前是全库召回：1,078 条 Intent 对 1,944 个 Action 打分排序；
- 回答的是“从共享库召回”，不是“在真实候选中选对”；
- 与上线任务不一致。

### 改进

1. **构建真实候选池**：
   - 同轨迹 + 同工具类型；
   - 同轨迹 + 邻近步骤；
   - 语义召回 Top-K；
   - 混合规则（推荐）。
2. **分档报告**：K = 5 / 10 / 20。
3. **报告候选覆盖率**：正确 Action 是否在候选池中，低于 90% 则规则需调整。
4. **保留全库评测**作为对比，两者并存。

---

## 二、Intent 处理：剔除模糊，不补全

### 问题

- 模糊 Intent 如“剩余 IP”“所有输出文件”缺对象、动作、范围；
- 补全等于替模型发明目标，评测不可信。

### 改进

1. **判定模糊**：对象不明、动作不明、范围不明、目标/手段混写。
2. **模糊即剔除**：不进评测集，不配负例。
3. **不补全**：只判断是否清晰，清晰则留，模糊则剔。
4. **反馈到抽取流程**：模糊 Intent 是数据质量问题，应推动上游改进。

---

## 三、指标升级：从 MRR 到步骤级一致性

### 问题

- MRR 只衡量排序能力，不衡量“这一步做得对不对”。

### 改进

1. **主指标**：步骤级一致性判断
   - 三分类：忠实执行 / 部分执行 / 未执行；
   - Accuracy、Precision、Recall、F1、Macro-F1、混淆矩阵。
2. **辅助指标**：候选覆盖率、Top-1、MRR@K。
3. **分组报告**：read / write / exec / search 各自指标。
4. **MRR 保留**：作为排序指标并列报告。

---

## 四、难负例构造：针对确认错误

### 问题

- 模型把“创建脚本”排成“运行脚本”；
- 把“检查文件”排成“下载文件”；
- 长 write 选错路径或内容。

### 改进

1. **三类难负例**：
   - 同动作不同对象；
   - 同对象不同动作；
   - 同工具不同参数。
2. **来源**：同轨迹其他 Intent、同工具类型、语义召回高分 Action。
3. **配比**：每个正例配 3–10 个难负例。
4. **不用随机负例**：随机负例对 BGE 太容易。

---

## 五、训练均衡：补 exec 覆盖

### 问题

- 训练以 read 为主，exec 只有 176 行；
- test 中 exec 最大且最弱。

### 改进

1. **补 exec 正例**：下载、运行脚本、验证文件、创建目录。
2. **补 exec 负例**：重点补“创建 vs 运行”“检查 vs 下载”。
3. **目标**：exec 训练行从 176 提到 600+。
4. **缺负例的正例**：先放 dev，不进 train。

---

## 六、流程规范：三方对齐 + 审核规则

### 改进

1. **三方对齐校验**：Thought → Intent → Action。
2. **先筛模糊 Intent**，再补全/去重/匹配。
3. **轨迹审核规则**：
   - Intent 只保留目标层；
   - 非平行 Intent 不参与单选；
   - 准备动作不算完成；
   - 只读操作不算额外操作；
   - 字段误标先修再入训练。

---

## 七、优先级与排期

| 优先级 | 任务 | 产出 |
|---|---|---|
| P0 | 局部评测 + 候选池构建 | local_report.json |
| P0 | 剔除模糊 Intent | intent_clear.jsonl |
| P1 | 难负例构造 | hard_negatives.jsonl |
| P1 | 补 exec 正例 | exec_balanced_train |
| P2 | 模型调参 | 最佳 checkpoint |

---

## 八、一句话总结

**当前改进方案 = 局部评测 + 剔除模糊 Intent + 步骤级一致性指标 + 难负例 + exec 均衡 + 三方对齐规范。**
核心变化是：评测从“全库召回”改为“真实候选下选对”，Intent 从“补全”改为“剔除模糊”，指标从“MRR”改为“步骤级 F1”，训练从“read 为主”改为“exec 补齐”。
