一、任务目标

数据落地流程与现有检索训练集的衔接见 `docs/2026-10-13-ta-coverage-data-processing-plan.md`。

本方案旨在利用小模型判断 Agent 的 Thought（思考意图）与 Action（实际工具调用）之间是否一致。

考虑到 Thought 可能包含多个 Intent，Action 也可能包含多个工具调用，因此将任务定义为：

从 Thought 中提取当前需要执行的 Intent，利用小模型判断 Action 对各 Intent 的语义覆盖关系，再根据整体覆盖程度，将 Thought–Action 一致性划分为一致、部分一致、不一致三类。

本阶段只关注 Action 调用是否在操作语义上覆盖 Intent，暂不验证 Action 是否执行成功，也不单独进行 Action 结构化解析。

二、整体技术路线

faithful / partial / not_executed

三、各阶段具体实现
阶段 1：Thought 中的 Intent 提取

首先从 Thought 中识别 Agent 当前准备执行的操作，并将其拆分为独立、可判断的 Intent。

例如：

Thought：

修改 config.yaml 的 timeout 为 30，并运行 pytest。

提取：

I1：修改 config.yaml，将 timeout 设置为 30。

I2：运行 pytest。

提取过程中重点处理三个问题：

1. 区分当前 Intent 与未来计划。

只有当前评测窗口内需要执行的 due-now Intent 才参与一致性判断。未来计划不应直接计入当前 Action 的覆盖范围。

2. 尽量保证 Intent 原子化。

一个 Intent 应尽量对应一个可独立判断的操作目标，避免把“修改配置并运行测试”整体视为一个 Intent。

3. 保留原始 Thought 证据。

每个 Intent 应记录对应的 Thought 原文片段，便于人工复核。

这一阶段可采用规则或小语言模型进行提取，再通过人工抽检验证准确性。

阶段 2：Intent 可评测性判断

提取出的 Intent 不一定都适合进行覆盖判断。

对于模糊 Intent，不建议在提取阶段直接删除，而应保留并记录不可评测原因。

如果一条 Thought 中所有 due-now Intent 均可评测，则进入后续流程。

如果只有部分 Intent 可评测，则保留局部覆盖信息，但不进入严格三分类主评测，避免因删除模糊 Intent 而人为提高一致性。

这一阶段需要建立统一的人工判定标准，并通过标注者一致性检验保证可复现性。

阶段 3：Intent–Action 覆盖关系建模

这是整个方案中最核心的模型训练环节。

不直接训练模型判断整条 Thought–Action 是否一致，而是将任务转化为更简单的二分类问题：

给定一个 Intent 和一个原始 Action，判断该 Action 是否在操作语义上完整覆盖该 Intent。

3.1 输入与输出

输入为：

一个原子 Intent 的文本。

一个 Action 的原始工具调用文本，包括工具名、命令及参数。

建议比较三种方案：

主要实验模型

推荐以 MiniLM Cross-Encoder 作为主要模型。

原因在于 TA 覆盖判断不仅要求语义相关，还要求识别操作类型、目标对象和参数值之间的差异。

例如“读取文件”和“修改文件”可能在语义空间中非常接近，但在操作覆盖意义上并不等价。

Cross-Encoder 通过联合编码 Intent 和 Action，更适合学习这种细粒度关系。

需要注意，模型是否更好仍应通过独立测试验证，不能仅凭架构推断。

四、小模型训练数据如何构造
4.1 数据来源

建议使用与最终测试 Gold 独立的 train 轨迹构造训练集。

训练数据的基本单位不是整条 Thought，而是一个 Intent–Action pair。

假设某条轨迹包含：

3 个 Intent

4 个 Action

则可以构造 12 个候选 pair。

但每个 pair 都需要独立的覆盖标签，不能直接将已有的 is_known_positive 或旧双塔排序结果当作真实覆盖标签。

4.2 正负样本构造

正样本应覆盖不同表达方式但操作等价的情况。

避免依赖文本相似度

训练时不能只依赖随机负样本。随机负样本通常容易区分，难以检验模型对真实 TA 混淆情况的判断能力。

建议第一轮尝试构建约 2,000–5,000 个经过质量控制的 pair，作为实验起点，后续根据数据质量和验证集表现调整。

4.3 标签获取方式

可以采用：

人工标注一部分高质量 pair。

利用明确规则生成高置信度候选标签。

使用较强模型辅助标注复杂 pair。

对自动生成的标签进行人工抽检和纠错。

需要特别注意，自动生成的标签属于弱监督数据，不应直接视为人工 Gold。

4.4 训练与验证划分

按照原始轨迹划分 Train、Dev 和 Test，避免同一 Thought 或高度相似的 Action 同时出现在不同数据集中。

训练集用于更新模型参数，Dev 用于选择模型和分类阈值，最终 Gold 只用于独立测试。

这一聚合方式简单、可解释，不需要额外训练三分类模型。

但有一个前提：每个原子 Intent 能够由单个 Action 独立覆盖。

对于必须由多个 Action 联合完成的 Intent，应尽量进一步拆分为原子子目标。如果仍无法拆分，则将其标记为复杂覆盖样本，暂不纳入第一版严格评测。

此外，当前二分类覆盖规则不专门检测额外的违背性操作，例如完成目标后又执行相反操作。这是 V1 的适用边界，应在实验报告中说明。



建议只做三个核心实验，保持训练数据、数据切分和评测口径一致。

E1

纯 BGE 双塔

使用 BGE 分别编码 Intent 和 Action，通过相似度判断覆盖关系。再增加一个监督微调版本，避免仅用通用相似度导致比较不公平。

回答：双塔经过任务微调后能达到什么水平？

E2

BGE + Code 双塔

Intent 使用 BGE，Action 使用合适的代码或命令编码器；通过监督训练对齐向量空间。

回答：专用 Action Encoder 是否带来可测量的收益？

E3

Cross-Encoder

将 Intent 和原始 Action 共同输入编码器，使用二分类头预测 covered / not covered。

回答：联合建模能否提升细粒度覆盖判断？

三个实验必须采用相同的独立 Train、Dev、Test 切分，并在 Dev 上分别确定阈值。最终比较：

Pair-level Precision、Recall、F1。

将覆盖关系聚合后的 TA 三分类 Macro-F1。

对“读取误判为修改”“参数值不一致”等难负例的错误率。

推理耗时和资源开销。

特别要确保 Test Gold 不参与模型训练或阈值选择。

五、还有一个更实用的选择：双塔召回 + Cross-Encoder 精判

如果你的数据量以后变大，可以考虑混合架构：

双塔快速计算候选 Intent–Action 相关性。

Cross-Encoder 对候选 pair 进行精细覆盖判断。

聚合覆盖结果，输出最终 TA 标签。

但这里存在一个风险：双塔可能漏掉词面不相似、实际却能覆盖 Intent 的 Action。如果采用候选筛选，必须先测量候选召回率；否则 Cross-Encoder 再准确也无法修复没有送入它的 pair。

如果每条轨迹只有几个 Intent 和 Action，直接计算所有 pair 通常更简单，也更适合第一版。

我的最终建议

第一阶段：优先训练 Cross-Encoder，同时建立一个经过监督微调的 BGE 双塔 baseline。

先不要默认方案 B 更好，也不必一开始就实现复杂的双塔对齐。等 E1 和 E3 的结果出来，再判断是否值得引入 Code Encoder。

最终选型应该看的是 TA 三分类 Macro-F1 的真实提升
